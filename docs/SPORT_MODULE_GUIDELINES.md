# 运动模块开发规范

本文档记录运动模块的统一实现契约和新增模块需求确认流程。系统整体架构见 [ARCHITECTURE.md](ARCHITECTURE.md)，前端规范见 [FRONTEND_GUIDELINES.md](FRONTEND_GUIDELINES.md)。

## 统一运动契约

- 主表命名为 `{sport}_records`，心得表命名为 `{sport}_notes`。
- 主表必须包含 `id/user_id/date/status/start_time/end_time/duration_s/remark/avg_heart_rate/max_heart_rate/calories/created_at/updated_at`；心得表必须包含 `id`、对应主表外键、`rating` 和 `notes`。
- 健身、游泳和舞蹈统一使用 `planned`、`recorded` 两种状态；统计只计 `recorded`。
- 表单（包括计划态）必须提供开始时间、结束时间和时长，三者均可为空。Excel、JSON 和 AI 导入也提供开始时间和结束时间；未填写时长时按起止时间推导。
- 列表和详情不按状态隐藏时间或时长；有值显示实际值，无值显示“—”。总览日卡中的计划态时长按 0 计算；心得仅在记录态且有内容时展示。
- Excel、JSON、AI 导入未填写结束时间时保持为空，不补当前时刻；手动新建仍沿用记录态默认时间规则。舞蹈时间字段统一称“上课时间”。
- 三个运动模块均提供列表、新建、编辑、删除、`/daily`、`/stats`、`/template`、`/import`、`/import-json`、`/ai-import`、`/batch-delete` 和心得接口。模块可增加专属字段、表和接口。
- 涉及统一规则的改动必须同步更新表单、导入导出、列表详情和总览，不能只修改其中一处。

## 新增运动模块需求确认

用户提出新增运动模块后，先阅读本文件和 `docs/ARCHITECTURE.md`，核对统一契约，再确认模块专属需求。用户已说明的内容不重复询问；完成确认后方可开发。

统一默认项无需确认：计划态和记录态均必填 `date`，状态分别为 `planned`、`recorded`。其他必填业务字段由用户决定。

需要向用户确认：

1. 模块中文名、英文标识、页面路径和 API 路径。
2. 主表字段，以及计划态、记录态各自的额外必填字段。
3. 心得表字段，以及是否需要动作、局数等专属表。
4. 是否需要统一接口之外的专属接口；Excel/JSON 导入如何归组主记录。
5. 当天卡、运动档案、全部记录、编辑、详情和总览需要展示的专属内容及统计口径。
6. 总览中的专属编码色；计划/记录状态色沿用 `--state-plan`、`--state-record`。

用户可以回答“无额外字段/表/接口/展示”，此时使用统一默认项。字段类型、空值、校验范围和布局由 AI 根据已确认需求设计，并与现有模块保持一致。

统一页面要求：当天卡、运动档案、全部记录、编辑与详情是最低页面范围；模块可按已确认需求增加专属展示。
