# 数据库建表设计（整改后结构）

> V2.0 模型骨架与 V2.1 一次性 AI 导入均未新增 AI 专属表、字段或索引；
> 模型配置及提示词分别存于 `.env` 和仓库文件，探针不持久化。
> 现有 AI 导入直接复用运动记录表写入，并非持久化草稿。
> V2.2 基础问答已落库：新增 `agent_conversations` 会话元数据表；消息不建消息表，
> 由 LangGraph PostgresSaver checkpointer 在独立 `langgraph` schema 的 4 张框架表
> 承载（checkpoint 能力提前到本版）。
> V2.3 数据问答**不新增表、字段或索引**：只读工具是进程内函数，复用现有运动、身材、
> 状态记录、生理周期与用户表查询；工具调用消息随 checkpointer 持久化。
> V2.4 Skill 管理新增 3 张表：`agent_skills`（技能主表）、`agent_skill_versions`（版本与
> 声明式定义）、`agent_skill_runs`（参数解析与执行审计）。V2.4 多角色另新增 2 张表：
> `agent_personas`（平台内置/用户私有角色，含工具/技能白名单）与 `agent_persona_versions`（人设提示词与发布版本）；
> 会话表增加角色绑定两列。V2.5 的长期画像拟用 LangGraph Store，V2.6 在已有 checkpointer 上做暂停追问。

> 库：`sports-health-platform`（PostgreSQL，连接串见 `.env`）
> 全库共 **28 张业务表**：1 认证 + 4 身材 + 3 训练 + 1 游泳记录 + 1 游泳心得 + 1 舞蹈记录 + 1 舞蹈心得 + 3 生理周期 + 4 状态记录 + 1 AI 会话 + 3 AI 技能 + 2 AI 角色 + 1 AI 报告 + 1 每日建议 + 1 健康档案；另有调度表 `scheduled_jobs` / `job_runs` 2 张与 `langgraph` schema 下 4 张 checkpointer 框架表（后者由应用 setup 管理），合计 34 张表。
> 三运动统一契约于 2026-11-06 迁移；全量 DDL 见 `scripts/schema.sql`，现有库运行 `scripts/migrate_sport_contract.py`；状态记录表现有库先运行 `scripts/migrate_state_record.py` 建表；表名统一 `state_` 前缀由 `scripts/migrate_state_table_prefix.py` 完成（新库直接执行建表脚本即得新名）。

RENAME` 不触碰数据行）。

> 变更记录（2026-11-17 健康/运动档案，幂等迁移 `scripts/migrate_health_profile.py`）：
> 20. 新增 `health_profile` 表：用户 1:1（`user_id` 直接作主键并 FK 引用 `users(id) ON DELETE CASCADE`）。`answers jsonb` 存「题目 key → 用户文本答案」，题目 key 与文案由 `app/modules/profile/questions.py` 定义（本版全部为开放式文本题，不做枚举、不校验选项，只限单题长度）；`completed_at` 记录达到完成题数（≥3 项）的时间，不足时为空。只存最新一份，不做版本历史；清空档案即删除该行。本表为「显式声明」的事实源，与后续对话推断的长期画像（LangGraph Store）职责不同，不互相替代。

> 变更记录（2026-11-18 V2.4 多角色，幂等迁移 `scripts/migrate_agent_personas.py`）：
> 18. 新增 `agent_personas` / `agent_persona_versions` 两表。平台角色按 `persona_key` 部分唯一、只读；用户角色按 `(owner_user_id, persona_key)` 部分唯一；`scope` 与 `owner_user_id` 由 CHECK 约束保持「system 无归属 / user 必有归属」；状态只允许 `active/disabled`。版本表按 `(persona_id, version_no)` 唯一，`definition` 为 `{schema_version:1, prompt}`。
> 19. `agent_conversations` 增加 `persona_id`（FK → `agent_personas(id)`，`NO ACTION`）、`persona_version_no`，并加 CHECK「两列同时为空或同时有值」。角色会话创建时写入两列，普通会话保持 NULL；删除被会话引用的角色由服务层返回 409，数据库外键兜底。

> 变更记录（2026-11-19 健康档案定制问题，幂等迁移 `scripts/migrate_health_profile_probe.py`）：
> 21. `health_profile` 增加 `custom_questions jsonb NOT NULL DEFAULT '{}'`，保存「健康档案测试」角色生成的多套问题：`{"sets":[{set_id, persona_key, generated_at, questions:[{key, local_key, group, label, hint, placeholder, max_length}]}]}`。答案继续写 `answers`，定制题 key 为 `probe_<set_id>_<qN>`，固定题 key 不变；同签名问题再保存只更新最新套答案，问题变化新增一套，最多 20 套，超出删除最旧一套及其答案。页面、API 与 Agent 只展示/使用最新一套。

> 变更记录（2026-11-19 内置角色工具/技能白名单，幂等迁移 `scripts/migrate_agent_persona_grants.py`）：
> 22. `agent_personas` 增加 `tool_grants jsonb NULL` 与 `skill_grants jsonb NULL`：`NULL` 表示沿用平台默认范围（`TOOL_PERSONA_SCOPES` + 未登记工具全开 + 平台技能全开），非空数组（含空数组）表示管理员显式白名单，空数组即不使用任何工具/技能。仅 `/api/system/system-personas` 管理员接口可写；普通用户角色编辑不涉及这两列。

```
agent_conversations 1──1 langgraph 线程（thread_id 对应 checkpointer 框架表，非外键，删除时 adelete_thread）

agent_skills 1──N agent_skill_versions（FK, ON DELETE CASCADE, UNIQUE(skill_id, version_no)）
agent_skills 1──N agent_skill_runs（FK, ON DELETE CASCADE）
users 1──N agent_skills（owner_user_id，仅用户私有技能）

```

- 约束：`PRIMARY KEY (id)`；索引：`ix_period_records_user_id`
- 设计要点：只存起止日期，经期长度与周期长度实时派生（周期长度 = 下一条开始日 − 本条开始日，无下一条为 null），不落库。阶段以「段」为唯一计算单元：段内排卵日 = 段长 − 14，黄体固定 14 天，卵泡期随段长伸缩。
- 段长规则：相邻首日间隔 < max(22, 参考周期 + 15) 拒绝保存（提示疑似同一次月经，请编辑已有记录）；22~45 为真实段；46~90 判漏记，按参考周期等分补推（余数摊前几段）；>90 不补推，两段间留白并提示漏记超过 3 个月。
- 预测范围：只推最新记录后的当前段与一个预测段，再往后留白；逾期 7 天内仍显示预测经期，超过转「未推算 + 建议补录」；0 条记录完全不推，1 条记录按参考值铺当前段 + 预测段。
- 四档状态由阶段内日序与疼痛等级实时推算；日历浅蓝绿/绿/黄/粉底色及窄屏两字状态名仅是前端展示映射，不存入 `period_records` 或其他周期表。
- 经期标注（period_state）不落库：落在记录窗口内为 recorded「经期」（有结束日按结束日，无结束日按参考经期从首日推导）；漏记补推段为 inferred「推算经期」；未来推算段为 predicted「预测经期」。

  - 硬删除：先 `adelete_thread` 清框架表，再删 agent_conversations 行。

    舞蹈 / 生理周期 / 个人资料，工具内独立短 session 查现有业务表，`user_id` 经 RunnableConfig 注入
    而非模型传入；取数范围与条数按意图可选、不传即全量（不设跨度 / 条数上限），工具调用与结果随 checkpoint 持久化。

- CHECK：`trigger_type IN ('cron','date','interval')`；`job_runs.status IN ('running','success','failed','skipped')`、`job_runs.source IN ('schedule','manual','cli')`。
- 两张表是实例级配置，不挂 `user_id`：任务对所有启用账号生效，归属隔离在业务函数内部（如报告任务只处理 `status=启用` 的用户）。
- 不使用 APScheduler 自带的 `SQLAlchemyJobStore`：任务定义只存本表，避免 job store 与业务表两套状态互相覆盖。

### 2.17 health_profile（健康/运动档案）

| 列 | 类型 | 空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| user_id | integer | NOT NULL | — | 主键 + FK → users.id，CASCADE |
| answers | jsonb | NOT NULL | `{}` | 题目 key → 用户文本答案（固定题见 `questions.py`，定制题为 `probe_<set_id>_<qN>`） |
| custom_questions | jsonb | NOT NULL | `{}` | 角色定制的多套问题（`sets`），仅最新一套展示 |
| completed_at | timestamp | 可空 | — | 达到完成题数（≥3 项）的时间；不足时为空 |
| created_at | timestamp | NOT NULL | now() | 创建时间 |
| updated_at | timestamp | NOT NULL | now() | 更新时间（ORM onupdate 自动刷新） |

- 约束：`PRIMARY KEY (user_id)`、`FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`；无额外索引（按主键查询）。
- 设计要点：
  - 题目 key 是本表的稳定契约：改文案只改 `questions.py`，改 key 会让旧答案失去归属，因此只加不改。
  - 本版全部为开放式文本题，不做枚举与选项校验，只限单题长度（100~255 字）；未知 key 与非文本一律拒绝。
  - 保存为合并语义：未传的题保持原值，空串清空该题；合并后一项不剩即删除整行（页面回到问卷态）。
  - 固定题只存最新一份、不做版本历史；`completed_at` 只表示「填够了」，不阻断保存。
  - `custom_questions` 保存「健康档案测试」角色生成的多套问题，一套问题一个 `set_id`，最多 20 套；同签名问题再保存只更新最新套答案，问题变化新增一套并保留历史，超出删除最旧一套及其答案。答案 key 为 `probe_<set_id>_<qN>`，固定题答案永不被该工具覆盖。
  - 页面、API 与 Agent 默认只展示和使用最新一套定制问题；历史套保留在库中但不参与展示。
  - 档案是**显式声明**的事实源，供页面、每日训练建议事实层与 Agent 只读工具读取；文本不做结构化解析，不参与代码硬约束判定。

## 3. 设计约定（需求口径落库方式）

1. **时长一律存秒、距离一律存米**（游泳/舞蹈 duration_s、distance_m）。
2. **派生计算值不落库**：BMI、配速、划频、趋势聚合、阶段推算均由 service 实时计算，避免脏数据。
3. **唯一索引支撑 upsert**：body（user+date，宽表一日一行）、pain（user+date）均建唯一约束，写入走"查重→更新或插入"。
   **三运动例外**：同日可多条计划/记录，按主表 `id` 增删改查。
4. **统一两态**：三运动 `status ∈ {planned, recorded}`。健身计划可经「完成训练」转为
   recorded；记录仍可编辑和删除，重复完成由接口拦截。
   游泳/舞蹈同构（默认 recorded）；API 层按模块校验业务必填字段：游泳计划需距离、记录需距离和时长；
   舞蹈两态均需舞种和星级，时长可空。健身两态均需至少一个具备动作名称的明细。
5. **归属与外键**：三运动主表 `user_id` 建 FK，删除用户时级联删除；请求仍按当前用户过滤。其余业务表依原有归属策略。
6. **多类型字段宽松化**：训练负荷（部位/重量/组数/个数）可空、每组个数为字符串、心得文本可空、游泳主泳姿可空——空值统一以 `NULL` 落库，前端以 "—" / "未填写" 展示，容量计算自动跳过空负荷动作。
7. 默认时间戳由 DB 生成（`now()`），updated_at 由 ORM `onupdate` 维护。
8. **状态记录不是运动模块**：食欲 / 肌肉疼痛 / 炎症 / 情绪四表不套 `SportRecordMixin` 与统一两态，无计划态、起止时间、时长、心率、热量；字段仅 id/user_id/date/star/remark/created_at/updated_at，同类一天一行唯一。性别开放（男女均可记录），男性或无周期记录时月历阶段置空。
9. **报告快照是 JSON 列**：`reports.facts` 存生成当时的事实快照（含扁平指标字典），派生值仍实时算但不回写业务表；`reports.narrative` 存结构化叙事。`data_hash` 只对 facts 做稳定哈希（剔除 `as_of`/`partial`），模型名与提示词版本不进 hash，避免无关变更触发重生成。
10. **定时任务是实例级配置**：`scheduled_jobs` / `job_runs` 不挂 `user_id`，任务对所有启用账号生效；内存作业不持久化，表是唯一事实源，启动时按表重建。
11. **健康档案是 1:1 单行 + 开放式文本**：`health_profile` 按 `user_id` 直接做主键，固定题答案存 `answers jsonb`，`completed_at` 只做完成标记；固定题不做版本表、不做 EAV。题目 key 与文案集中由 `app/modules/profile/questions.py` 定义，页面渲染、后端校验与 AI 读取共用同一份定义。角色定制问题另存 `custom_questions`，答案仍写 `answers`，只保留最新一套参与展示。
